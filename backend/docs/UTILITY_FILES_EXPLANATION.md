# Utility Files Explanation

This document explains the purpose and importance of the utility files in the backend root directory.

---

## Overview

These files are **CLI utility tools** that form a **semantic layer generation pipeline**. They are **NOT part of the main application runtime**, but are **essential for creating and updating** the `semantic.json` file that the main application depends on.

---

## The Pipeline Flow

```
dbt manifest.json
    ↓
manifest_reader.py
    ↓
metadata.json (compact metadata)
    ↓
inference_engine.py
    ↓
inferred.json (with dimensions, measures, etc.)
    ↓
semantic_generator.py
    ↓
semantic.json (final format)
    ↓
Main Application (reads semantic.json)
```

---

## File-by-File Breakdown

### 1. `manifest_reader.py` 📖

**Purpose**: Extracts metadata from dbt's `manifest.json` file

**What it does**:
- Reads dbt's `target/manifest.json` (generated by dbt after running models)
- Extracts model information (tables, columns, descriptions, tags)
- Filters models based on tags or name patterns
- Outputs a compact `metadata.json` file

**Usage**:
```bash
python manifest_reader.py \
  --manifest target/manifest.json \
  --out metadata.json \
  --filter-tag wide
```

**Why it's important**:
- Connects your dbt data models to the semantic layer
- Extracts column descriptions and metadata from dbt
- Allows filtering to only include specific models (e.g., "wide" tables)

**When to use**:
- After running `dbt compile` or `dbt run` (which generates `manifest.json`)
- When you want to update the semantic layer with new dbt models
- When you add new columns or tables to your dbt project

---

### 2. `inference_engine.py` 🧠

**Purpose**: Intelligently infers dimensions, measures, time columns, and derived measures from metadata

**What it does**:
- Takes `metadata.json` (from manifest_reader)
- Uses heuristics to classify columns:
  - **Numeric columns** → Measures (e.g., `amount`, `price`, `quantity`)
  - **Date columns** → Time columns (e.g., `date`, `created_at`)
  - **String columns** → Dimensions (e.g., `name`, `category`, `status`)
- Optionally samples the database to get actual column types
- Generates derived measures (e.g., `SUM(amount)`, `AVG(price)`)
- Creates quality rules (e.g., flag invalid amounts)
- Outputs `inferred.json` with all classifications

**Usage**:
```bash
python inference_engine.py \
  --metadata metadata.json \
  --out backend/metadata/inferred.json \
  --use-db-sampling  # Optional: sample DB to get real types
```

**Why it's important**:
- **Automates semantic layer creation** - no manual classification needed
- Uses intelligent heuristics based on column names
- Can optionally verify types by sampling the database
- Generates common derived measures automatically
- Creates quality rules for data validation

**When to use**:
- After running `manifest_reader.py`
- When you want to regenerate the semantic layer
- When you add new columns and want them automatically classified

---

### 3. `semantic_generator.py` 🔧

**Purpose**: Converts inferred metadata into the final `semantic.json` format

**What it does**:
- Takes `inferred.json` (from inference_engine)
- Transforms it into the exact format expected by the main application
- Structures data as: `{tables: {table_name: {columns, dimensions, measures, ...}}}`
- Outputs `semantic.json` in the correct location

**Usage**:
```bash
python semantic_generator.py \
  --inferred backend/metadata/inferred.json \
  --out backend/metadata/semantic.json
```

**Why it's important**:
- **Final step** in the pipeline
- Ensures `semantic.json` is in the correct format
- The main application **depends on this file** to understand your data structure
- Without this file, the application cannot generate SQL queries

**When to use**:
- After running `inference_engine.py`
- This is the **final step** before the main application can use the semantic layer

---

### 4. `start_api.sh` 🚀

**Purpose**: Convenience script to start the FastAPI application

**What it does**:
- Activates the virtual environment
- Starts the uvicorn server on port 8000
- Enables auto-reload for development

**Usage**:
```bash
./start_api.sh
```

**Why it's important**:
- Quick way to start the API server
- Handles virtual environment activation
- Useful for development and testing

## How These Files Relate to the Main Project

### Connection to Main Application

1. **Main Application Reads `semantic.json`**:
   - `FileSemanticRepository` loads `metadata/semantic.json`
   - `SemanticService` uses this to understand table/column structure
   - `QueryService` uses semantic layer to generate SQL from natural language

2. **Without `semantic.json`, the application cannot work**:
   - The application needs to know:
     - What tables exist
     - What columns are in each table
     - Which columns are dimensions vs measures
     - What time columns exist
     - What derived measures are available

3. **These utility files CREATE `semantic.json`**:
   - They are run **before** starting the main application
   - They are **one-time setup** or **update tools**
   - They are **NOT imported** by the main application code

## Complete Workflow Example

### Initial Setup (First Time)

```bash
# 1. Run dbt to generate manifest.json
cd /path/to/dbt/project
dbt compile  # or dbt run

# 2. Extract metadata from dbt manifest
cd /path/to/backend
python manifest_reader.py \
  --manifest /path/to/dbt/target/manifest.json \
  --out metadata.json \
  --filter-tag wide

# 3. Infer dimensions, measures, etc.
python inference_engine.py \
  --metadata metadata.json \
  --out backend/metadata/inferred.json \
  --use-db-sampling

# 4. Generate final semantic.json
python semantic_generator.py \
  --inferred backend/metadata/inferred.json \
  --out backend/metadata/semantic.json

# 5. Start the application
./start_api.sh
```

### Updating Semantic Layer (When Schema Changes)

```bash
# 1. Re-run dbt after schema changes
cd /path/to/dbt/project
dbt compile

# 2. Re-run the pipeline
cd /path/to/backend
python manifest_reader.py --manifest ... --out metadata.json
python inference_engine.py --metadata metadata.json --out ...
python semantic_generator.py --inferred ... --out backend/metadata/semantic.json

# 3. Reload in application (or restart)
# The SemanticService has a reload_semantic_layer() method
```

## Importance Summary

### ✅ **Critical for Application Functionality**

- **Without `semantic.json`**: The application cannot understand your database structure
- **Without these tools**: You would have to manually create `semantic.json` (very tedious)
- **These tools automate** the entire semantic layer generation process

### ✅ **Separate from Runtime**

- These are **CLI tools** (run from command line)
- They are **NOT imported** by the main application
- They are **one-time setup** or **maintenance tools**
- They run **before** the application starts

### ✅ **Part of Data Pipeline**

- They connect your **dbt models** → **semantic layer** → **main application**
- They enable the **natural language to SQL** functionality
- They make the system **self-documenting** (uses dbt descriptions)

## When to Run These Tools

### Initial Setup
- ✅ First time setting up the project
- ✅ After cloning the repository
- ✅ When `semantic.json` doesn't exist

### Regular Updates
- ✅ After adding new tables/columns in dbt
- ✅ After modifying dbt model descriptions
- ✅ When database schema changes
- ✅ When you want to refresh the semantic layer

### Not Needed
- ❌ During normal application runtime
- ❌ For every API request
- ❌ When only querying data (semantic.json already exists)

## Conclusion

These utility files are **essential infrastructure tools** that:
1. **Automate** semantic layer generation
2. **Connect** dbt models to the main application
3. **Enable** natural language to SQL functionality
4. **Reduce** manual work significantly

They are **kept in the root directory** because they are:
- CLI tools (not part of the application code)
- Run independently (not imported)
- Part of the setup/maintenance workflow

**Without these tools, you would have to manually create and maintain `semantic.json`, which would be very time-consuming and error-prone.**
