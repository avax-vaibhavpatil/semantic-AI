PROJECT BRIEFING: What We're Building & What's Next
================================================================================

OUR OVERALL GOAL:
-----------------
Transform a working prototype into a PRODUCTION-READY, SCALABLE, and 
MAINTAINABLE enterprise application using modern software architecture principles.

What the Application Does:
--------------------------
This is an "Auto Semantic BI Platform" - it allows users to:
1. Ask questions in natural language (e.g., "Show me sales by region")
2. AI converts questions to SQL queries automatically
3. Executes queries on the database
4. Returns results in a user-friendly format
5. Saves favorite queries as "reports" for later use

The Magic:
----------
- User asks: "Which branch has highest sales?"
- AI generates: SELECT branch_name, SUM(sales) FROM ... GROUP BY branch_name
- System executes query and returns results
- User can save this as a "Sales by Branch" report

WHAT WE'VE COMPLETED SO FAR (Foundation Layers)
================================================================================

✅ 1. CONFIG LAYER (app/config/)
   Purpose: Centralized configuration management
   What we built:
   - Settings management (Pydantic-based, type-safe)
   - Database connection configuration
   - Logging setup (structured JSON logs)
   - Environment variable handling
   
   Why it matters:
   - Single source of truth for all settings
   - Easy to change config without touching code
   - Production-ready (supports .env files, secrets management)

✅ 2. CORE LAYER (app/core/)
   Purpose: Business domain models and rules
   What we built:
   - Report model (saved queries with metadata)
   - Query models (request/response structures)
   - Semantic layer models (tables, columns, measures)
   - Business exceptions (ReportNotFoundError, etc.)
   - Constants (MAX_QUERY_ROWS, etc.)
   
   Why it matters:
   - Pure business logic (no database, no API)
   - Reusable across different interfaces
   - Easy to test
   - Clear business rules

✅ 3. INFRASTRUCTURE LAYER (app/infrastructure/)
   Purpose: External systems integration
   What we built:
   
   a) Database Infrastructure:
      - Async database connections (asyncpg)
      - Query executor (execute_query, stream_query)
      - Connection pooling
      
   b) AI Provider Infrastructure:
      - Abstract AI provider interface
      - Claude provider (Anthropic)
      - Groq provider
      - OpenAI provider
      - Smart router with fallback (Claude → Groq → OpenAI)
      - Retry logic for retryable errors
   
   Why it matters:
   - Can swap AI providers easily
   - Handles failures gracefully (fallback)
   - Async = better performance
   - Isolated from business logic

✅ 4. REPOSITORIES LAYER (app/repositories/)
   Purpose: Data access abstraction
   What we built:
   - ReportRepository (save, get, list, search, update, delete reports)
   - SemanticRepository (load semantic layer from JSON)
   - Abstract interfaces (contracts)
   - Async implementations using SQLAlchemy Core
   
   Why it matters:
   - Business logic doesn't know about database
   - Can swap database without changing business code
   - Easy to test (mock repositories)
   - Clean separation of concerns

WHAT'S NEXT: SERVICES LAYER (app/services/)
================================================================================

CURRENT STATE:
--------------
We have:
- ✅ Data access (Repositories)
- ✅ External integrations (Infrastructure)
- ✅ Business models (Core)
- ✅ Configuration (Config)

We're MISSING:
- ❌ Business logic orchestration
- ❌ Use case implementation
- ❌ Validation and error handling
- ❌ The "glue" that connects everything

WHAT WE'RE BUILDING NEXT:
--------------------------
The Services Layer will contain:

1. QueryService
   - Takes user's natural language question
   - Loads semantic layer
   - Calls AI provider to generate SQL
   - Validates SQL
   - Executes query
   - Returns results
   - This is the CORE business logic!

2. ReportService
   - Saves user queries as reports
   - Retrieves saved reports
   - Lists user's reports
   - Searches reports
   - Updates/deletes reports
   - Executes saved SQL queries
   - Orchestrates ReportRepository

3. SemanticService
   - Loads semantic layer
   - Reloads semantic layer (when file changes)
   - Validates semantic layer
   - Provides semantic layer to other services

WHY SERVICES LAYER IS CRITICAL:
---------------------------------
Right now, if we wanted to handle a user query, we'd have to:
1. Load semantic layer (call repository)
2. Generate SQL (call AI provider)
3. Execute query (call database)
4. Handle errors
5. Format response

This logic would be scattered in API routes (bad!).

With Services Layer:
- All business logic in one place
- API routes just call services
- Easy to test business logic
- Can reuse services from different interfaces (API, CLI, etc.)
- Clear separation: API = HTTP, Services = Business Logic

EXAMPLE FLOW (After Services Layer):
-------------------------------------
User asks: "Show me sales by region"

API Route (app/api/v1/query.py):
  → Receives HTTP request
  → Calls: query_service.execute_query(question="Show me sales by region")
  → Returns HTTP response

QueryService (app/services/query_service.py):
  → Loads semantic layer (semantic_repository)
  → Generates SQL (ai_router)
  → Validates SQLlet
  → Executes query (database executor)
  → Returns results

Clean! Each layer has one job.

WHY THIS ARCHITECTURE?
================================================================================

BEFORE (Old Structure):
-----------------------
backend/
  sql_agent.py (814 lines - everything in one file!)
  - API routes
  - Business logic
  - Database calls
  - AI calls
  - Configuration
  - Everything mixed together!

Problems:
- Hard to test
- Hard to understand
- Hard to change
- Hard to scale
- Hard for new developers

AFTER (New Structure):
----------------------
backend/app/
  api/          → HTTP handling only
  services/     → Business logic only
  repositories/ → Data access only
  infrastructure/ → External systems only
  core/          → Business models only
  config/        → Configuration only

Benefits:
- ✅ Easy to test (test each layer independently)
- ✅ Easy to understand (clear responsibilities)
- ✅ Easy to change (change one layer, others unaffected)
- ✅ Easy to scale (add new services, new APIs)
- ✅ Easy for new developers (clear structure)

================================================================================
KEY PRINCIPLES WE'RE FOLLOWING
================================================================================

1. SEPARATION OF CONCERNS
   Each layer has ONE job:
   - API = HTTP handling
   - Services = Business logic
   - Repositories = Data access
   - Infrastructure = External systems

2. DEPENDENCY INJECTION
   Services receive dependencies (repositories, AI providers)
   Not hardcoded - easy to test and swap

3. INTERFACE-BASED DESIGN
   Code depends on interfaces, not implementations
   Can swap implementations easily

4. SINGLE RESPONSIBILITY
   Each class/function does ONE thing well

5. TESTABILITY
   Each layer can be tested independently
   Use mocks for dependencies
